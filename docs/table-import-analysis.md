# Markdown 表格导入方案分析

日期：2026-10-30。本文为方案分析，没有新增表格转换功能，也没有执行 B 站表格上传或发布验证。

后续已实现表格转 PNG，当前支持范围和验证进度见[实现说明](table-import.md)。下文保留方案分析时的比较。

## 结论

以当前“B 站专栏不支持原生表格”的限制为前提，建议增加两种明确可选的转换方式：默认将表格渲染为 PNG，保留表格外观；另提供逐行转换为带字段名的列表，保留文字、链接和原生公式的可编辑性。暂不自动按列数猜测用户想要哪种方式。

表格图片本来就应独占一块，不会遇到行内公式图片无法嵌入文字的问题。但图片中的单元格文字无法作为正文直接选择复制，链接不能单独点击，公式也不再是原生可编辑公式；需要修改时，应修改原 Markdown 后重新生成并导入。

## 方案比较

| 方式 | 表格外观 | B 站内编辑 | 适用情况 | 主要限制 |
| :---: | :---: | :---: | :---: | :---: |
| PNG 图片 | 可以保留边框、表头、对齐和样式 | 编辑整张图片及题注 | 一般对照表、数据表 | 单元格文字和公式变为图片内容，宽表手机阅读困难 |
| 逐行字段列表 | 改为列表或段落 | 文字、链接和公式可继续编辑 | 字段说明、记录表、链接较多的表 | 横向比较不如表格直观，表头重复、正文变长 |
| 等宽代码块 | 近似字符网格 | 可以编辑纯文本 | 很小的纯文本或数字表 | 中文宽度、长文本及换行难处理，不能保留丰富样式和原生公式 |
| LaTeX array / 矩阵 | 适合小型数学数组 | 可以编辑整条 TeX 公式 | 数学矩阵、小型数值表 | 通用中文和富文本表格不适合，命令兼容性需在 B 站验证 |
| HTML table / CSS 布局 / 客户端表格插件 | 浏览器局部可能显示 | 取决于平台文档模型 | 不作为首选交付方案 | 客户端显示不等于保存、预览及发布后能保留 |

ProseMirror 的文档内容由 schema 定义，并通过 schema 解析 DOM 和序列化文档。仅让 Markdown-it 输出 `<table>` 或直接插入 DOM，并不能证明平台支持持久化表格。客户端新增表格节点还需要保存、恢复、预览和发布链路共同支持；目前没有这方面的 B 站验证证据。[ProseMirror 官方指南](https://prosemirror.net/docs/guide/#schema)

## 与当前项目的接入方式

当前 `planImport()` 已在导入前取得原始文档和 Markdown-it 解析器，`prepareImages()` 沿用 B 站 `uploadHandler(File)`，`importFiles()` 在所有准备成功后才调用原生导入。因此表格处理应增加到这个异步准备阶段，而不是给同步的 `FileReader.result` getter 或粘贴监听器加入异步渲染。

建议流程：

1. 读取文档、提取首行标题、保护美元公式，使用启用了表格规则的 Markdown 解析器取得 token，识别真实表格，跳过 fenced code 和行内代码示例。当前 B 站解析器的表格规则是否启用尚未重新核对；不能依赖已被原生预处理清理后的结果，必要时使用独立解析器。
2. 从表格节点取得表头、单元格内容与列对齐。首版只承诺普通管线表格；HTML 合并单元格等不直接纳入。
3. 生成受控样式的表格布局，完成字体、单元格公式和图片的准备，再输出 PNG `Blob/File`。保留左、中、右列对齐、粗体、斜体、删除线和代码文字。
4. 将表格对应的源文本范围替换为生成图片的临时引用；不改磁盘上的原 Markdown。通过 token 的源位置处理，避免用简单按行切分或正则误伤转义竖线、代码和其他内容。
5. 将生成图片加入本次导入的资源清单，与本地图片一起预检查、上传，默认不加水印；按转换后的总图片数量核对当前账号限制。
6. 上传结果通过现有 `imageHtml()` / `withImageRenderer()` 生成原生图片节点，表格仍放在原文位置，沿用题注、图片前空段落处理和提交后核对。
7. 渲染、上传或核对失败时停止替换正文，显示具体表格及原因；导入完成后保存并重开草稿，检查图片及前后文顺序。

当前普通 `.md` 原生导入的公式保护仍可同步执行；表格图片的生成和上传通常需要异步处理。首版应先在自定义导入面板支持，不承诺仅替换 FileReader getter 就能无感支持 B 站原有文件导入入口。

## 图片渲染的选择

第一种是浏览器内转换：在临时布局容器渲染表格，再通过 HTML 转 Canvas 的库导出 PNG。优点是用户仍只操作当前导入面板；缺点是新增浏览器依赖，需要处理字体就绪、CSS 支持及图片跨域。html2canvas 根据 DOM 和样式重建画面，并非浏览器真实截图，不支持全部 CSS；跨域资源也可能导致无法导出。因此首版应限制为简单、受控的表格样式，并明确处理表内图片和公式，而不是任意网页截图。[html2canvas 官方说明](https://html2canvas.hertzen.com/documentation)

第二种是本地预处理：先用本地命令生成 `table-assets/*.png` 和转换后的 Markdown，再使用已有文件夹导入。现有项目安装了 `sharp` 和 Node 端 `mathjax-full`，有利于复用公式 SVG 渲染与图片输出；但它们不是浏览器里的现成接口，仍需实现表格布局与混排。离线工具更容易控制字体和公式渲染，也可考虑本地浏览器渲染后截图；代价是多一次命令操作。

浏览器方案更贴近现有使用体验，本地方案适合先验证复杂表格及数学内容。不能把 SVG / Base64 留在正文里当作最终上传结果，应生成平台接受的普通图片并完成原生上传。

## 必须提前解决的细节

- **手机可读性**：提高 PNG 像素密度只能改善清晰度，不能改变宽表缩小后的文字大小。长表应按完整行分页并重复表头；宽表可按列分组并重复标识列，或由用户选择字段列表模式。不能把任意宽表强行缩到正文宽度后称为适配完成。
- **单元格公式**：生成表格图片前先渲染 TeX，且保留单元格所在列。表外公式仍走现有原生公式链路；表内公式最终是表格图片的一部分，不能再单独编辑。
- **表内图片**：应先决定是否支持。首版可以明确报错并指出表格位置；支持时需读取已授权文件或满足跨域条件的资源，避免漏图。表格内已被合成的图片不应在正文中再次独立上传或重复插入。
- **链接**：图片模式只保留显示文字。可选在图片后附来源链接清单；不能承诺图片中的每个链接仍可点击。列表模式可保留原生超链接。
- **字体和背景**：使用可用的中文字体，等待字体加载，输出明确的浅色背景与深色文字。白底图片在夜间模式中仍是白底，这比透明底下文字可能不可读更可控。
- **数量和大小**：分页后每一张图都计入图片数量，复用现有文件大小检查。预检查应显示“识别到几张表、将生成几张图片”，超限时在上传前停止。
- **可追溯性**：本地保留原 Markdown；可下载生成图和转换结果。图片题注用于说明表名或分段编号，不承担存储完整表格源代码的职责。

## 建议的首版范围及验收

建议首版支持普通管线表格、中文与数字、列对齐、基本字符样式、自动换行、长表分图及表内美元公式；提供“图片”和“字段列表”两种模式，默认图片。宽表先明确提示并允许改用列表；HTML 合并单元格、任意 CSS 和表内图片作为后续能力，不静默丢内容。

测试至少覆盖转义竖线、空单元格、代码中的伪表格、中文长文本、不同列对齐、表内公式与表外原生公式共存、链接、重复表格、分页后的图片限制和上传失败保护。浏览器验收应同时核对桌面、手机预览、保存重开和原文前后顺序；在完成这些验证前，不能将方案分析写成已上线支持。
